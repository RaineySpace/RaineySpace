# 登记博客项目

把项目维护分成“调查、抓取、对比确认、写入、验证”五个阶段。无论项目是否已经登记，都完成官方基础信息抓取。确认是强制阶段门；用户明确批准新增或更新之前，保持仓库只读。

## 遵守协作边界

- 只使用可追溯的官方信息；区分页面明示事实、合理推断和待确认内容。
- 不照抄大段营销文案。将已核实的核心价值改写成简洁、克制的中文描述。
- 不猜测项目定位、发布日期、用户规模或商业状态。
- 不因为项目地址可访问就视为用户已经批准写入。
- 发现现有登记、URL 重复或内容冲突时先报告，不创建第二条记录。
- 不修改作为 GitHub 主页的 `README.md`，不改变静态导出架构，不提交或发布，除非用户另有明确要求。

## 阶段一：检查当前状态

1. 读取 `content/projects.json`、`lib/projects.ts` 和 `scripts/validate-content.mjs` 中与项目有关的规则；以当前代码为准，不依赖技能内的旧快照。
2. 搜索 `public/*/index.md` 的 `projectId`，确认项目是否已经登记、是否已有可关联文章，以及候选 ID 或 URL 是否冲突。
3. 记录工作树状态。保留用户的既有改动，只触碰本次确认范围内的文件。
4. 规范化输入 URL 用于查重，但保留项目官方使用的 canonical URL 作为展示地址。

记录项目是“已存在”“不存在”还是“登记不完整”，但不要因为已经存在而停止。无论当前状态如何，都继续抓取官方基础信息。若只存在文章或只存在 registry 条目，将其标为登记不完整，后续提出补全方案，不能重复创建。

## 阶段二：从官方来源抓取信息

打开用户提供的地址，并按需检查同域页面、页面元数据、结构化数据、品牌资源和官方文档。必要时搜索以定位官方页面，但最终候选事实必须回到官方来源核验。

收集以下候选字段：

- `projectId`：简短、稳定、全小写的 kebab-case 标识；不能因展示名变化而轻易变化。
- `name`：项目正式名称；只有页面稳定使用副标题时才保留副标题。
- `url`：可访问的官方 HTTP(S) 地址，去掉无意义的追踪参数。
- `date`：项目自身日期，格式 `YYYY-MM-DD`。不要猜测上线或发布时间；没有官方明示或用户确认时向用户询问，不要用关联文章日期冒充。
- `description`：一句中文简介，说明目标用户、核心问题和主要能力；只保留官方来源能支撑的内容。
- `cover`：可选。优先稳定的官方 HTTPS Logo/封面；不能确认稳定性时留空，让现有首字母占位生效。不要使用搜索结果缩略图、临时签名 URL 或非官方重制图。
- `pinned`：默认建议 `false`，但必须让用户确认。

同时记录每个事实对应的官方来源。若官网依赖登录、拒绝访问或关键信息含糊，说明缺口并只向用户询问会改变最终条目的 1–3 个问题；不要用推断补空。

## 阶段三：对比状态并请求确认

完成抓取后，先把官方候选信息与当前博客逐字段对比，再根据状态选择确认方式。

### 项目已存在

1. 明确告知用户项目已经登记，并给出 registry 条目和关联文章的位置。
2. 展示 `projectId`、`name`、`url`、`date`、`description`、`cover`、`pinned` 的“当前值 / 官网候选值 / 建议”对比。没有官方依据的可选字段标为“未核实”，不要擅自清空现有值。
3. 明确列出保持一致、发生漂移、当前缺失和仅来自用户配置的字段。即使没有差异，也要说明“当前信息与官网一致”。
4. 询问用户是否需要更新信息。存在差异时给出推荐更新对象和确切文件；没有差异时询问是否保持现状，或是否仍要调整置顶等用户配置。
5. 在用户明确回复“确认更新”及更新范围前停止。不要把同一项目作为新项目再添加。

### 项目不存在

1. 明确告知用户当前博客尚未登记该项目。
2. 展示将写入 `content/projects.json` 的完整候选对象、官方来源、未核实字段和将新增或修改的文件。
3. 询问用户是否需要新增项目，并在用户明确回复“确认新增”前停止。
4. 新增项目必须同时确定博客文章关联方案，保证 registry 条目至少被一篇文章通过 `projectId` 引用。

### 为新增或登记不完整项目确定博客文章关联方式

项目 registry 中的每个项目必须至少被一篇文章通过 `projectId` 引用。检查后推荐以下一种方案：

1. **关联已有文章**：只在文章确实介绍或复盘该项目时，给它增加 `projectId`。
2. **新建项目介绍页**：默认保存到 `public/<slug>/index.md`，使用 `hidden: true` 使页面可直达、从文章列表/Feed/Sitemap 隐藏，同时仍出现在项目集合中。

新建介绍页时，提出并确认：

- `slug`、`title`、`date`、`summary`、`tags`、`projectId`；
- `date` 表示这篇博客页面的发布日期，不冒充项目发布日期；
- 正文将采用的已核实要点；用户个人动机、经历和判断没有来源时标为待用户补充，不替用户编造；
- 本地资源与文章放在同一目录，并以 `./asset.ext` 引用；项目卡片封面若要本地化，则使用 `public/` 下稳定的站点绝对路径。

为新增项目或登记不完整的现有项目，用紧凑的确认单展示：

- 输入地址与最终采用的官方来源；
- 将写入 `content/projects.json` 的完整候选对象；
- 选择“关联已有文章”或“新建项目介绍页”，以及对应的 frontmatter 和正文摘要；
- 尚未核实的字段、会新增或修改的文件；
- 明确询问用户是否确认新增、确认补全，或希望修改哪些字段。

用户修改了会影响展示、排序或文章内容的字段后，更新确认单并再次确认。不要把“看看这个项目”“抓一下信息”等调查请求当成写入授权。

## 阶段四：执行确认后的改动

收到“确认更新”“确认新增”或“确认补全”等明确授权后，先重新读取目标文件，防止确认期间发生漂移，再按确认分支做最小且完整的修改：

1. **更新现有项目**：只修改用户确认的字段，保留稳定的 `projectId` 和现有文章关联；除非关联缺失且用户确认补全，否则不新建文章。
2. **新增项目**：向 `content/projects.json` 写入确认过的完整对象，并关联已有文章或创建已确认的 `public/<slug>/index.md`。
3. 只使用当前 schema 允许的 `name`、`url`、`date`、`description`、`cover`、`pinned`。
4. 文章 frontmatter 只写 `projectId`，不要重复 `projectName`、`projectUrl`、`projectDescription` 或 `projectCover`。
5. 新文章至少包含 `title`、`date`、`summary`、`tags` 和 `projectId`；按确认结果设置 `hidden: true`。
6. 只写已核实或用户亲自确认的正文。信息不足时缩短页面，不用泛化文案填充。
7. 若确认使用本地封面，检查响应确实是目标图片而非 HTML 错误页，再保存到约定路径；不要留下抓取临时文件。

保持 JSON 现有缩进和字段风格。若 registry 或文章在写入前出现与确认方案冲突的新改动，停止并向用户说明差异。

## 阶段五：验证并交付

依次运行：

```bash
pnpm validate:content
pnpm build
git diff --check
```

若项目的 `mise` 环境没有自动生效，改用 `mise exec -- pnpm validate:content` 和 `mise exec -- pnpm build`。验证失败时先判断是本次问题还是已有问题；只修复本次范围内的问题。

最后检查 diff，确认：

- registry URL 与 `projectId` 没有重复；
- 项目至少有一篇引用文章；
- 名称、简介、链接、封面、置顶状态和文章可见性与确认单一致；
- 没有修改 `README.md` 或混入无关文件。

交付时列出新增或修改的文件、项目最终展示信息、文章关联方式、实际执行的验证及已有警告。不要声称未执行的检查已经通过。

## 识别典型请求

- “把 `https://example.com` 这个项目添加到博客。” → 无论是否已登记都先抓取；已存在时对比并询问是否更新，不存在时询问是否新增。
- “这是代码仓库地址，帮我收录为项目。” → 使用仓库中可核实的项目资料，继续寻找并核实官方产品地址；没有独立官网时，请用户确认是否将仓库地址作为项目 `url`。
- “信息没问题，确认新增。” → 重新检查文件后写入 registry 和文章关联，并完成验证。
- “确认按官网更新。” → 只更新对比单中已确认的现有字段，不重复新增项目或文章。
- “只更新项目描述，不要新建文章。” → 先重新抓取并对比；确认后仅更新描述，不扩大到其他字段或新建内容。
